# LaslesVPN: сервер, база и полноценный вход (подпроект 1 из 5)

Дата: 2026-10-01 · Статус: на согласовании

## Контекст и цель

Сейчас LaslesVPN — фронтенд-демо (React 19 + Vite 8 + react-router 8 + TS 6, EN/RU).
«Вход» хранится только в `localStorage`, паролей нет. Пользователь хочет **рабочее демо**,
то есть продукт, который ведёт себя как настоящий: свой сервер и база, настоящая регистрация,
вход и роли, а затем бэк-офис. Оплата остаётся тестовой. Запуск локальный, но проект должен
выкатываться позже без переделок.

Работа разбита на 5 подпроектов, у каждого свои spec, план и реализация:

1. **Сервер, база, авторизация** — этот документ.
2. Каркас бэк-офиса `/admin`, роли, журнал действий, управление клиентами.
3. Подписки и платежи: тестовая оплата, возвраты, выручка, экран успешной оплаты.
4. Серверы VPN: управление из админки, сайт берёт их из базы.
5. Обращения (формы Help/Partners/Affiliate) и подписчики рассылки.

**Подпроект 1 готов, когда:**
- `npm run dev` одной командой поднимает фронтенд и API с локальной базой (без Docker);
- регистрация, подтверждение email, вход, выход, сброс пароля, смена email, удаление аккаунта,
  вход через Google (если заданы ключи) и 2FA (TOTP) работают на `/` и `/ru` через `/dev/mail`;
- личный кабинет (обзор, устройства, оплата, настройки) и оформление заказа работают через API,
  а `localStorage` больше не хранит аккаунты;
- серверные интеграционные тесты, существующие тесты, lint, build и `i18n:scan` проходят.

## 1. Архитектура и запуск

| Часть | Решение |
|---|---|
| HTTP-сервер | **Hono** на Node 25, TypeScript запускается напрямую (type stripping), отдельная сборка в разработке не нужна |
| Авторизация | **Better Auth**: email и пароль, подтверждение email, сброс, Google OAuth, плагин `twoFactor` (TOTP и резервные коды), плагин `admin` (роли, бан) |
| База | PostgreSQL через **Drizzle ORM**. Локально **PGlite** (встроенный Postgres, файлы в `.data/`), в продакшене `DATABASE_URL`. Диалект и миграции одни и те же |
| Валидация | **zod** на всех наших эндпоинтах |
| Письма | интерфейс `Mailer`. В разработке письма пишутся в таблицу `dev_mail` и в консоль, страница `/dev/mail` показывает их. В продакшене SMTP через `SMTP_*` |

**Структура:**
- `server/index.ts` — запуск;
- `server/app.ts` — Hono-приложение;
- `server/auth.ts` — Better Auth;
- `server/db/` — схема, подключение, миграции, сид;
- `server/mail/`;
- `server/routes/` — `/api/me/*`, `/api/checkout`, `/api/dev/mail`;
- `shared/` — тарифы, `PlanId`, типы ответов API. Общий код фронта и сервера, переносится из `src/data/plans.ts`, кроме картинок.

Пакет `package.json` один.

**Разработка:**
- `npm run dev` запускает Vite и API (`:3001`) параллельно. Vite проксирует `/api/*`, поэтому для браузера всё на одном адресе;
- `npm run db:reset` пересоздаёт базу;
- при старте автоматически применяются миграции, затем выполняется сид.

**Сид** создаёт:
- администратора `admin@laslesvpn.test`;
- демо-клиента `demo@laslesvpn.test` с тарифом Standard, двумя устройствами и тремя платежами.

Пароли берутся из `.env` (`SEED_ADMIN_PASSWORD`, `SEED_DEMO_PASSWORD`) с понятными значениями по умолчанию в `.env.example`.

**Продакшен** (на будущее): один Node-процесс отдаёт `build/` и `/api`.

**`.env`** (в git не попадает, есть `.env.example`):
- `BETTER_AUTH_SECRET`, `APP_URL`, `DATABASE_URL` (необязательно);
- `GOOGLE_CLIENT_ID` и `GOOGLE_CLIENT_SECRET` необязательны: без них кнопка Google скрыта (фронт узнаёт об этом через `/api/config`);
- `SMTP_*` (необязательно).

## 2. Данные и сценарии

### Таблицы

- **Better Auth:** `user` (+ `role`: `customer|admin|support|finance`, `banned`, `banReason` из плагина admin; `locale`: `en|ru`), `session`, `account`, `verification`, `two_factor`.
- `subscription`: `userId` (уникальный), `plan` (`free|standard|premium`), `billing` (`monthly|yearly`, null для free), `status` (`active|canceled`), `renewsAt`, `createdAt`.
- `payment`: `id` (вида `INV-…`), `userId`, `plan`, `billing`, `amount` (в центах, integer), `cardBrand`, `cardLast4`, `status` (`succeeded`), `createdAt`.
- `device`: `id`, `userId`, `name`, `platform`, `createdAt`.
- `preferences`: `userId` (PK), `autoConnect`, `killSwitch`, `newsletter`.
- `dev_mail`: `id`, `to`, `subject`, `text`, `html`, `createdAt`. Используется только в разработке.

Все дочерние таблицы удаляются каскадно вместе с пользователем.

### Сценарии

1. **Регистрация:** имя, email, пароль от 8 символов (проверка на сервере), письмо подтверждения
   на языке страницы. Войти можно сразу. В кабинете висит плашка «Подтвердите email» с кнопкой
   «Отправить ещё раз». **`/api/checkout` отвечает `email_not_verified`, пока email не подтверждён.**
2. **Подтверждение:** ссылка из письма ведёт на `/verify-email?token=…` (или `/ru/verify-email`),
   там показывается результат: успех, ссылка истекла или ссылка недействительна.
3. **Вход:** email и пароль. Ошибка всегда общая (`invalid_credentials`). Включён rate-limit
   Better Auth. Заблокированный пользователь получает `account_banned`.
4. **Сброс пароля:** `/forgot-password` → ответ всегда «если аккаунт есть, мы отправили ссылку» →
   письмо → `/reset-password?token=…` → новый пароль и подтверждение. Токен одноразовый и
   живёт 1 час. После сброса все сессии отзываются, затем переход на вход с подставленным email.
5. **Google:** кнопка на входе и регистрации. Если email совпадает с подтверждённым аккаунтом,
   Google привязывается к нему (account linking по доверенному провайдеру).
6. **2FA:** включается в «Настройках»: пароль → QR-код и секрет → ввод кода → 10 резервных кодов.
   При входе с включённой 2FA открывается шаг `/login/2fa` (код или резервный код). Отключение
   требует пароля. Обязательность 2FA для сотрудников проверяется в подпроекте 2.
7. **Сессии:** cookie `httpOnly`, `SameSite=Lax`, `Secure` в продакшене, срок 30 дней. В «Настройках»
   есть список активных сессий и «Выйти на всех устройствах».
8. **Смена email:** письмо на новый адрес, смена происходит только после подтверждения.
   **Смена имени** — сразу. **Смена пароля** требует текущий пароль.
9. **Удаление аккаунта:** нужно ввести слово-подтверждение (как сейчас) и пароль, затем удаляются
   все данные.
10. **Роли:** регистрация через сайт всегда даёт `customer`. Сотрудники создаются сидом, а позже
    в бэк-офисе. Серверный helper `requireRole(...roles)` появляется уже здесь, вместе с тестом.
11. **Старые демо-данные:** ключи `laslesvpn.session` и `laslesvpn.accounts` в `localStorage`
    удаляются при первом запуске новой версии. Аккаунты не переносятся.
12. **Язык писем:** `user.locale` выставляется при регистрации по языку страницы и обновляется,
    когда пользователь переключает язык в залогиненном состоянии. Письма шаблонные, EN и RU.

### API (наши эндпоинты; авторизация — стандартные `/api/auth/*` Better Auth)

| Метод и путь | Что делает |
|---|---|
| `GET /api/config` | `{ googleEnabled, devMail }` |
| `GET /api/me` | профиль, подписка, настройки |
| `PATCH /api/me` | имя, locale |
| `GET /api/me/devices` · `POST` · `DELETE /:id` | устройства (лимит по тарифу, `device_limit`) |
| `GET /api/me/payments` | история платежей |
| `PATCH /api/me/preferences` | автоподключение, Kill Switch, рассылка |
| `POST /api/me/subscription/cancel` | отмена, переход на free в конце периода |
| `POST /api/checkout` | `{ plan, billing, card: { number, expiry, cvc, name } }` → сумму считает сервер, карта не сохраняется (только бренд и last4), тестовая карта `4000 0000 0000 0002` даёт `card_declined` |
| `GET /api/dev/mail` | только в разработке |

## 3. Фронтенд, ошибки, тесты

### Фронтенд

- `src/auth/` переходит на `createAuthClient` из Better Auth (`better-auth/react`) с клиентскими
  плагинами `twoFactor` и `admin`. `useAuth()` сохраняет форму (`user`, `signIn`, `signUp`,
  `signOut`, `updateUser`, `deleteAccount`), методы становятся async, добавляется `loading`.
  `RequireAuth` показывает загрузку, пока сессия не известна.
- `src/api/`: `apiFetch` (JSON, `credentials: 'include'`, разбор `{ error: { code } }` в
  `ApiError`), хуки `useMe`, `useDevices`, `usePayments`. Без сторонних библиотек запросов.
- Новые страницы, EN и RU через существующий i18n и `usePageMeta`: `/forgot-password`,
  `/reset-password`, `/verify-email`, `/login/2fa`, `/dev/mail` (только при `devMail: true`).
  В «Настройках» добавляются блоки: двухфакторная защита, активные сессии, смена email, смена
  пароля.
- `Checkout` отправляет запрос на сервер. Валидация формы на клиенте остаётся для удобства, но
  решает сервер.

### Ошибки

- Единый ответ `{ error: { code: string } }` с HTTP-статусом. Коды: `invalid_credentials`,
  `email_not_verified`, `account_banned`, `token_expired`, `token_invalid`, `weak_password`,
  `email_taken`, `device_limit`, `card_declined`, `validation_failed`, `rate_limited`,
  `unauthorized`, `forbidden`, `not_found`, `server_error`. Фронт показывает `t.errors[code]`;
  для неизвестного кода — `t.errors.server_error`.
- Сеть недоступна → `t.errors.network` и кнопка «Повторить». 401 на защищённой странице →
  переход на вход с `next`.
- Изменяющие запросы проверяют `Origin` против `APP_URL`. Каждый `/api/me/*` работает только с
  данными текущего пользователя.

### Тесты

- **Сервер** (Vitest, PGlite в памяти, чистая база на каждый файл): регистрация → письмо в
  `dev_mail` → подтверждение → вход; неверный пароль → `invalid_credentials`; сброс (одноразовость,
  истечение, отзыв сессий); 2FA (включение, вход с кодом, вход с резервным кодом); `requireRole`
  (customer → 403); checkout (сумма от сервера при подменённой цене, `card_declined`,
  `email_not_verified`); устройства (лимит, чужое устройство → 404); удаление аккаунта каскадом.
- **Фронт:** существующие тесты; `apiFetch` (коды ошибок, сеть); `i18n:scan` чистый.
- **Вручную:** сквозной проход всех сценариев на `/` и `/ru` через `/dev/mail`.
